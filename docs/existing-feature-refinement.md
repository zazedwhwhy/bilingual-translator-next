# 0.3.1：借鉴FluentRead优化已有功能

基线为本项目43d528d/0.3.0；竞品静态依据固定在2f0fb198，见`fluentread-optimization-reference.md`。本版独立实现已有功能的性能和正确性改进，没有复制竞品代码或增加学习账户/新翻译服务。

## 借鉴了什么

| 已核实的FluentRead机制 | 本项目原问题 | 0.3.1改进 |
| --- | --- | --- |
| 热层命中后，把LRU访问时间在32ms窗口合并写回 | 即使命中内存，也等待一次持久写入 | 热命中不再等待访问时间落盘；合并touch后再写。冷命中仍需读取数据库。 |
| 同一真实悬停候选只更新鼠标坐标，保留首次计时 | 同段内轻微移动不断重设450ms，难以触发 | 同段/同文本保留原截止时间，到期仍用最新坐标重核；聚焦任何输入（含排除的敏感字段）不触发悬停。 |
| 输入提交核对目标/编辑代次/原文，选区有失效与手动快照例外 | 旧输入请求可能挡住新输入入口；空目标错误后旧结果仍返回；新选区取消滞后 | 切换输入目标取消旧预览；显式输入请求先作废旧请求再读新快照。新的非空Range立即使旧请求失效，即使文字相同也核对完整起止节点/偏移；已打开手动卡片在失选时仍可读。 |

FluentRead的翻译value本身仍逐key写入，不能把它说成通用结果批写。本项目另外在自己的Jobs→Cache路径把一批最多8条结果改成一次写事务、一次容量维护，取代逐条写入/逐条维护。网页、文件、字幕共用该路径。

## 缓存正确性与失败行为

缓存仍为30天、1000条，数据库保持原version1结构，服务/模型/语言/提示版本隔离键不变。内存读取/提升与批写都维护有界LRU。无效或空的持久记录不能当作译文，按可观察miss处理，后续真实请求仍受权限和额度检查。

clear先递增代次、清空内存/touch和计时器，再按顺序等待已有写入并执行持久清理。等待中的旧hash/read/write/touch不能在清空完成后复活数据。清理异常仍向调用方报错；不会显示已清空。Jobs在等待本批缓存处理后再次检查取消，停止的任务不能迟到报告完成。

持久读写发生异常时保留真实提供方/内存译文，并在结果或后续状态中显示“缓存读写异常，重复翻译可能再次请求”。异步touch失败不取消已经有效的译文。不会自动换服务、重试、退还未知计费或把空数据当翻译成功。
